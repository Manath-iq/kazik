# Общие столы · 06.11.2026

## Кто принимает решения

`CasinoRoom`, SQLite-backed DO, детерминированное имя `public-v1:roulette` / `public-v1:crash`. Не один глобальный объект для всех игр. Crypto RNG, UUID и все границы фаз — серверные. Betting 10с → playing (roulette 5с, Crash до секретной точки) → result 4с → новый раунд. Никакой автоповтор ставки. В браузере только обратный отсчёт и визуальная интерполяция.

JSON состояния и следующий alarm сохраняются одной DO transaction до публикации. Конструктор не перезаписывает будильники. Нет setInterval на сервере. Alarms продолжают цикл без подключённых клиентов; cron раз в 15 минут — watchdog/первичное создание. Первый вход также создаёт стол сразу. При долгом сбое не создаются тысячи прошлых пустых раундов: заканчивается сохранённый раунд, затем начинается новый 10-секундный приём.

## Деньги и повторные запросы

Миграция `0006_shared_casino.sql` добавляет только новую таблицу, индексы и triggers. Старые пользователи, кошельки, runs/Stars и ledger не переписываются.

- INSERT ставки и trigger-списание в ledger — одна D1 transaction. CHECK кошелька запрещает double-spend даже между разными играми, городом и вылазкой.
- UUID key + request hash: идентичный retry безопасен; чужой/изменённый payload — 409. `UNIQUE(user_id,round_id)` — одна ставка на общий раунд.
- Deadline повторно проверяется триггером **в D1 после сетевой задержки**, а не только до запроса в DO.
- UPDATE accepted → won/lost/cashed_out и ledger-начисление — одна транзакция. Уникальный ref и запрет изменений завершённых ставок не позволяют выплатить повторно.
- Crash: никакой клиентский multiplier не принимается. Cashout берёт время обработки в DO и дополнительно проверяет D1 commit < crash deadline. На равенстве — проигрыш. Задержка сети не гарантирует вывод по видимому коэффициенту.
- Разрыв DO/D1 не является распределённой транзакцией: D1-решение идемпотентно, DO повторяет settlement. Если запись D1 прошла, а DO не успел сохранить result, повтор обновит только ещё accepted ставки. Новый раунд не начинается до завершения выплат. Пачки по 100 сохраняют ограниченный объём работы.
- Существующий потолок кошелька 1 млрд **учётных единиц** сохраняется. Ошибка/квота/переполнение не урезает выигрыш молча: settlement остаётся на повторе; нужны восстановление ресурса/разбор владельцем, а не отмена ставки.

## Синхронизация и приватность

HTTP state возвращает только текущую/предыдущую **свою** ставку и баланс. Roulette number раскрывается после блокировки ставок, перед вращением. Crash point/deadline не входит в playing state; phaseEndsAt=null. WS публикует только общий round/serverNow/recent, не пользователей или балансы. Все проигрыши отключённых игроков рассчитываются alarm.

Короткий одноразовый ticket (30с, hash в DO storage) выдаётся после обычной авторизации. Основная сессия не передаётся в URL. Upgrade проверяет Origin; ticket потребляется атомарно очередью комнаты. WS read-only, ping/pong обслуживается Hibernation API. При background socket закрывается, при resume/reconnect — новый ticket и свежий HTTP snapshot. Отключённая панель не принимает новые ставки. Лимит 250 соединений на стол; публичная ёмкость не обещается без метрик.

## Совместимость и выпуск

Новые индивидуальные roulette/spin и crash/start возвращают понятный 409 «обнови игру»; завершённые idempotent retries и старые Crash cashout/history остаются. Blackjack и его expiry не удалены. Прежние ставки в истории доступны отдельно; переход не уничтожает уже списанные деньги.

Конфиги prod/test/local содержат `durable_objects` и `new_sqlite_classes` migration `casino-v1`. D1 0006 применить **до** деплоя кода. Не откатывать DO migration; не удалять namespace при rollback. Пользоваться прежним тестовым Worker и той же D1, не копировать проект.
